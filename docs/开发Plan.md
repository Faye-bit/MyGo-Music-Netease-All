# MyGo 网易云音乐插件开发 Plan

制定日期：2026-11-08。

需求来源：[项目 README](../README.md)。技术依据：[接口调研](接口调研-20261108.md)。状态：第一阶段 0.1.0 的开发、安装包和 36 项模拟验证已完成；已安装到本机并完成独立扫码、歌单读取与单曲播放抽样，重启恢复也已通过，完整验收仍有未验证项。详见 [第一阶段验收记录](验收记录-阶段1.md)。第二阶段 0.2.0 开发与本机核心展示/播放抽样已完成，模拟验证及未验证项见 [第二阶段验收记录](验收记录-阶段2.md)；第三阶段 0.3.0 插件侧开发已完成，完整五档待宿主支持；真实音源样本及缓存验收仍有未验证项，详见 [第三阶段验收记录](验收记录-阶段3.md)。

## 1. 目标与实现路线

严格按 **登录 → 首页 → 音质** 三个阶段推进。第一阶段的“登录”包含独立替代所必需的歌单同步与原有功能基线；第二、三阶段分别改善首页和音质，不在最后才补登录插件的原有能力。

基于现有网易云插件代码改进，保留许可证和来源说明，发布为可独立安装的插件。运行时不依赖旧插件，不默认要求用户运行额外 API 服务、Node 或外部播放器。MyGo 负责界面、播放与音频缓存，插件负责网易云会话、数据和音源。

官方开放平台具有部分匹配能力，但是否完整覆盖尚未验证。阶段一安排有时间上限的接口验证；首版暂以已存在的客户端接口路线规划。若官方路线通过全部关键门槛，再整体调整接入方案，不默认混用两套身份体系。

菜单栏播放卡片不属于本计划。第三阶段若需要宿主音质支持，仅处理实现音质需求所必需的协议、设置、缓存和标识，不扩大到其他主程序改造。

## 2. 技术组织与交付原则

- 发行包以 `plugin.json` 和单入口 `index.js` 为核心。开发代码可按请求、会话、目录、首页、播放划分模块；拆分前先验证宿主加载方式，必要时打包成单文件，避免假定支持 Node API。
- 请求层统一负责普通请求/EAPI、超时、错误分类、Cookie 更新和有限重试；业务层不散落请求编码逻辑。
- 会话拥有递增版本标识；退出、切换账号或重新登录后，旧请求不得覆盖新会话或数据。
- 会话存于宿主插件存储；不把 Cookie、私钥、完整鉴权响应写入日志、测试样例或仓库，不声称普通存储具备系统钥匙串保护。
- 缓存按账号隔离；登录状态变化时清理推荐、喜欢列表及进行中的音源请求。业务缓存与宿主音频缓存分开设计。
- 初期使用独立插件 ID，保留旧插件作为回退。新 ID 会影响宿主收藏/队列中来源引用，因此默认重新登录和云端同步；不自动复制旧会话，也不自动改写宿主数据。最终 ID 在首个可用版本前固定。
- 单元测试使用模拟宿主和脱敏响应；网络验收单独记录，模拟通过不能替代真实账号验收。

## 3. 阶段一：登录与完整替代基线

预计 3–5 个有效工作日，其中接口与环境验证约 0.5–1 天。

### 3.1 前置验证

1. 核对本机 MyGo、现有插件版本和功能入口，冻结功能清单；对照调研中的源码提交，记录差异。
2. 验证 MyGo 的二维码提示、插件存储、网络权限、加密函数和无损音源基础链路；确定 `minAppVersion`，不凭最新版本号猜最低版本。
3. 若官方文档与开发者凭据可用，核对用户授权、歌单分页、日推、完整音源和音质字段。凭据由用户在本机配置，不在聊天中收集私钥。
4. 官方路线选择门槛：完整替代功能齐全、音源可由 MyGo 消费、身份与 ID 可映射、应用密钥部署方案明确。若无法验证，记录原因并继续客户端接口路线；这不等于认定开放平台“不支持”。
5. 固定上游代码基线，保留 LICENSE 与 THIRD_PARTY_NOTICES，并建立可安装包和测试入口。

### 3.2 实现任务

- 扫码登录状态：待扫码、待确认、成功、过期、取消、超时；成功后校验账号再持久化。
- 重启后恢复会话；登录失效时提示重登。内容无权限与会话失效分开处理，避免歌曲不可播就退出账号。
- 退出只清除本插件会话与相关缓存，不影响官方客户端；取消后到达的旧轮询结果不得重新登录。
- 分页读取自建与收藏歌单，保持分类、顺序和 ID；同步“我喜欢的音乐”及喜欢状态。
- 歌单按完整曲目 ID 分批补详情，消除静默截断。超大歌单先验证宿主整页加载的性能；无法完整加载时明确显示已加载/总数和原因，不标记为完整同步成功。
- 将“同步”定义为读取云端最新状态及用户明确触发的写操作，不新增后台自动双向合并或自动批量修改。
- 保留既有搜索、播放、歌词、喜欢、歌单增删曲目等能力；写入成功后重新读取核对，失败不盲目重试。

### 3.3 完整替代功能清单

以下为调研版本公开导出函数，最终还需与安装版本核对。阶段一保留行为，后续阶段只增强相关项。

| 功能组 | 必须保留的插件入口 |
| --- | --- |
| 账号 | `account`、`signIn`、`signOut` |
| 检索与目录 | `search`、`album`、`artist` |
| 歌单 | `playlists`、`playlist`、`addToPlaylist`、`removeFromPlaylist` |
| 喜欢 | `liked`、`isLiked`、`like` |
| 首页与浏览 | `home`、`browse`（发现、日推、雷达、个性化歌单、榜单） |
| 连续推荐 | `stations`、`stationNext` |
| 播放与内容 | `stream`、`lyrics`、`comments` |
| 播客 | `shows`、`show` |

上述基线没有公开导出创建/删除/重命名歌单、评论写入或播客订阅写入，不因为宿主支持这些方法就自动扩大需求。隐藏的心动模式候选不当作已上线功能。

### 3.4 验收与交付

- 停用旧插件后，新插件能独立登录、搜索、播放、读取歌词和同步歌单。
- 验证重启、退出、二维码过期、取消、网络中断、账号切换，以及旧请求延迟返回。
- 用官方客户端核对自建/收藏/喜欢列表与歌单顺序；超过一页的列表和超过 1000 首的歌单有真实样本则实测，无样本须明确记录并补模拟测试。
- 喜欢/取消喜欢、增删曲目只在用户指定测试歌单和测试曲目上验收，验证云端结果并恢复测试数据。
- 原有功能逐项记为通过/失败/未验证；关键账号、歌单、播放失败不得进入“可替代”状态。
- 交付：可安装的第一阶段版本、功能对照表、脱敏验收记录、已知问题。

## 4. 阶段二：首页个性化与展示

预计 2–3 个有效工作日；依赖第一阶段账号和播放链路通过。

### 4.1 实现任务

1. 登录后读取日推，将歌曲放入 `home().sections[0].tracks`，复用宿主日推大卡片、播放按钮与悬停动效；日推详情页复用同批数据。
2. 首页推荐歌单使用登录后的个性化推荐接口。未登录时显示登录提示或明确标为普通推荐的内容，不伪装个性化成功。
3. 日推封面取真实推荐歌曲；雷达读取对应歌单封面；私人漫游若没有可信封面则用中性占位，不为装饰而提前消费推荐队列。
4. 保留雷达、漫游、榜单等入口，并验证私人雷达是否随账号变化；不自制随机歌单冒充官方推荐。
5. 将不同分区的失败隔离，推荐歌单失败不使日推和播放入口全部消失；登录失效统一由会话层处理。
6. 日推缓存按账号和日期区分，提供手动刷新；服务端结果为准，不假定跨午夜必然更新，也不未经验证固定为每天 6 点刷新。退出/切换账号立即失效。
7. 对首页请求去重、限制并发，优先复用已取得的歌曲详情，避免每次进入页面重复整批拉取。

### 4.2 验收与交付

- 首页实际出现日推大卡片，封面对应歌曲，点击进入和播放顺序正确；实机确认悬停动画。
- 同账号、相近时间与官方客户端比较日推及推荐歌单，记录差异，不能要求不同请求时刻结果逐项永久一致。
- 测试未登录、推荐为空、部分请求失败、跨日、切换账号和手动刷新。
- 连续推荐不会因展示封面而跳过首批歌曲；重复返回有去重和终止保护。
- 交付：首页增强版本、前后截图、接口对照和性能观察记录。

## 5. 阶段三：音质适配

插件侧预计 2–4 个有效工作日；完整五档宿主适配另计 2–4 天，不含上游合并等待。

### 5.1 先验证音源，再扩展 UI

1. 建立候选映射：标准 `standard`、较高 `higher`、极高 `exhigh`、无损 `lossless`、Hi-Res `hires`。其中现有实现没有验证的档位需先实测，不直接标成支持。
2. 对可用账号与歌曲建立样本矩阵：普通可播、会员可播、无损、Hi-Res、无对应档位、仅试听、无权限、失效地址。
3. 音源记录区分请求档位与实际返回档位，并保留 `type`、`bitRate`、大小以及服务端提供的其他必要信息。未返回的采样率/位深不虚构。
4. 校验完整音源和解码；`freeTrialInfo`、空 URL、内容权限错误必须明确处理。无损/Hi-Res是账号与歌曲共同决定，不能只看会员身份。
5. 缺少目标档位时，可接受服务端返回的有权限完整低档音源并准确标识；客户端额外降档只针对已确认的档位不可用，限定次数。鉴权失败、风控、限流、超时不能靠逐档请求掩盖。
6. 合并同曲同档进行中的请求；地址过期时重新取流。退出账号后旧地址/结果不进入新账号业务缓存。

### 5.2 两层交付边界

**A. 现有宿主上的插件交付**

- 稳定支持宿主传入的三档偏好，按实际返回值报告无损/有损。
- 验证设置从下一首歌曲生效及缓存行为。
- 不把 `lossless` 暗中等同 `hires`，不通过文本偏好绕过宿主缓存后宣称完成五档适配。

**B. 达成 README 完整五档目标的配套工作**

- 为宿主扩展音质枚举、设置选项、传参和实际播放标识，保持旧插件三档兼容。
- 更新音质缓存排序、键和元数据处理，验证旧缓存兼容；明确“允许复用更高音质缓存”还是“严格匹配所选档位”的行为，并展示实际播放档位。
- 覆盖“先缓存普通无损，再选择 Hi-Res”“先高档缓存，再选低档”“换账号后缓存权限语义”等场景。
- 在配套测试构建上完成验收，再向上游讨论/提交独立音质支持改动。计划本身不授权现在发布 Issue 或 PR。
- 如果当前只开发插件而暂不做配套宿主工作，第三阶段必须标为“插件侧完成，完整五档待宿主支持”，不能宣布 README 全部完成。

### 5.3 验收与交付

- 每个已宣称支持的档位，记录至少一个有权限的真实样本及实际返回信息；没有合适账号/曲目时记为未验证。
- 缓存命中与重新取流均不出现请求档位冒充实际音质、试听冒充完整播放的问题。
- 测试切歌、重启、失效地址、限流和没有高音质权限的情况。
- 保留第一、二阶段回归：账号、歌单、首页、搜索、歌词、喜欢与基本播放。
- 交付：音质增强插件、样本矩阵、宿主依赖清单；若包含配套修改，另附宿主改动和验收记录。

## 6. 测试与发布方式

测试优先覆盖有业务风险的行为：二维码状态机、会话竞态、分页/顺序、写操作幂等风险、推荐缓存隔离、音源权限及实际档位。模拟 `host` 和 `fetch` 做确定性测试，使用 MyGo 实机检查插件加载、存储和展示。网络测试默认不进入普通单元测试。

每阶段维护 `docs/验收记录-阶段N.md`，包含版本、环境、测试账号类型（不含凭据）、用例、预期、实际、证据和未验证项。完成实际测试后才填写“通过”，本计划中的任务不视为已执行。

安装和回退：导出可安装包，记录插件版本与宿主要求；先保留旧插件，再停用它验证新插件独立运行。不要删除旧数据或升级覆盖旧插件作为首次验证方式。发布远端仓库和提 PR 在相应交付阶段另行执行。

## 7. 时间与阶段门槛

| 阶段 | 有效开发时间 | 进入下一阶段前的条件 |
| --- | --- | --- |
| 一：登录与替代基线 | 3–5 天 | 独立登录、歌单和基本播放实测通过，原有能力有对照记录 |
| 二：首页 | 2–3 天 | 日推卡片、个性化数据及账号隔离通过 |
| 三：音质插件侧 | 2–4 天 | 三档准确播放、候选五档验证、缓存限制清楚 |
| 三：五档宿主配套 | 额外 2–4 天 | 选项、传参、缓存、显示与实际音源一致 |

合计：插件侧约 **7–12 个工作日**；包含完整五档配套约 **9–16 个工作日**。按每天约 6 小时有效开发估算，复用现有实现，优先在用户的 Mac 验收。另预留约 20% 接口变化与联调缓冲；开发者入驻、账号授权、缺失测试样本及上游审阅等待不计入有效开发时间。

若首次实测发现登录/完整音源接口不可用，先定位并重新评估接入路线，不继续堆叠首页和音质选项。若官方 API 最终要求不同部署架构或无法满足关键功能，应更新本计划与接口调研，保留证据，不把未验证能力写成已支持。
